Why h33-h33-2-b2 scored 0.2778 [owner-report] and whether we can beat it

Metric DTI = TPw/(TPw+0.2·FPw+0.8·FNw), triangular kernel k(d)=max(1−d/300m,0), one credit max per truth pixel, known USGS/INGENIOUS faults masked from scoring [official] DrivenData 306/967 and 11516/11536. Verified implementation vendor/gems57/metric.py.

  • H19-5 solid = 121,131 line pixels, D2.8 = 44,090 binary dots at ≥√8 px (2.83 px min, 3.0 px median), H33 = D2.8 minus 6,436 dots ≤2 px from catalogue = 37,654 dots — all dots on H19-5 lines [measured] evidence/forensics_h33_vs_d28.json. Scores 0.1922→0.2600→0.2778 [owner-report] registry/family_scores.csv.
  • All three top files are binary 0/1 [measured] — optimum is vertices because DTI is ratio of linear functions per pixel. Break-even credit per dot =0.2·DTI ≈0.055 at 0.2778 [measured] metric.py.
  • The climb is emission geometry on one detector: near-flank dots earn mean credit <0.055 each, so pruning ≤2 px from catalogue helps (organizer masks known faults). H33 median distance to catalogue 19.6 px vs D2.8/ H78-A 6.0 px [measured].
  • To beat 0.2778 the field must rank candidate pixels by more kernel credit per dot on unmapped faults, not just thin the same field. Current holdout best 0.1826 [HOLDOUT-DTI gems57-pooled-hide-v2 s20 n=11321] and 0.1898 [same evaluator, lidar-augmented, not significant vs 0.1843] are not leaderboard projections.
  • Beating it would require a detector that finds unmapped faults >300m from mapped ones with higher precision; the holdout shows far-truth (>10 px from visible) level is only ≈0.06 for every arm, so generalisation far from catalogue is weak.

PhD judgement: 0.2778 is plausible because owner-reported chain matches measured geometry and metric algebra, but it is not ORGANIZER-CONFIRMED in this repo (GEMSDOE32 page fetched 2026-10-21 says no organiser score, IR-78-20). The only way to know live gain is an organizer receipt.
